# 議事録

## 経緯の確認

discovery.md が指摘した「try はあるが catch がない」パターンを確認する前に、過去の議論を辿った。
「API失敗時のエラー状態の具体的な表示」は
[0004: home and login](../0004-home-and-login/proposal.md) で最初に別トピックへ先送りされ、
[0010: item groups](../0010-item-groups/proposal.md)、
[0011: items crud](../0011-items-crud/proposal.md) でも同様にスコープ外とされ続けていた。
今回のバグ報告は、3回連続で先送りしてきた領域を実際に踏み抜いた結果であることを最初に共有した。

## コード調査で追加した論点

discovery.md は書き込み系(`GroupNewPage`・`GroupEditPage`・`ItemNewPage`・`ItemEditPage` の
create/update/delete)の catch 欠如に絞って書かれていたが、コードを読むと以下も同じ根の問題だった。

- `GroupsListPage`・`GroupDetailPage`(アイテム一覧)の GET 失敗が `catch` で空配列をセットしており、
  「0件」と「取得失敗」が同じ表示になる。
- `GroupEditPage`・`ItemEditPage` の初期ロード(`getGroup`/`getItem`)、および
  `GroupDetailPage`(グループ本体)・`ItemDetailPage` の GET 失敗は `catch` で `null` をセットするのみで、
  `if (!group) return <Skeleton />` という分岐のため、**失敗時はローディング中の骨組みが永久に表示され続ける**
  (ローディングでもエラーでもない不定状態)。これは discovery.md 本文が挙げた「ボタンが無反応に見える」より
  一段質の悪い症状だと判断し、追加の論点として提示した。

## 質問と回答

1. **スコープは書き込み系のみか、読み込み系(GET失敗時の誤表示)も含めるか。**
   → 読み込み・書き込み両方を対象にする。「API失敗時に何をどう見せるか」という方針自体を決める議論なので、
   GET の誤表示だけ切り離す理由がない。

2. **エラーの見せ方はトースト通知か、フォーム内インラインか、使い分けるか。**
   → フォーム内インライン表示を採用。トースト通知は既存プロジェクトに通知ライブラリ(sonner 等)が
   一切入っておらず、導入コストに見合う理由がないため見送った。

3. **discovery.md が触れている 401(セッション切れ)を、0010 の「AppLayout での一括ガードは設けず一般エラーとして扱う」方針のまま踏襲するか、専用扱い(自動ログイン画面リダイレクト等)にするか。**
   → 一般エラーとして扱う既定路線を踏襲する。401 専用のリダイレクト機構は見送った
   (0010 で一度検討済みの選択肢を蒸し返さない)。

4. **GET失敗時の表示は既存の `EmptyState` を拡張するか、新規コンポーネントにするか。**
   → 新規 `ErrorState` コンポーネントを作る。`EmptyState` は「0件+作成CTA」という責務が明確なので、
   そこにエラー表示の責務まで混ぜると variant 分岐が増えて読みにくくなる、という理由で拡張案を見送った。

5. **エラーメッセージは常に汎用文言か、API(huma)が返す detail をそのまま表示するか。**
   → 常に汎用日本語メッセージを採用。API 側のエラーメッセージは英語で実装詳細に近い文言
   (例: `"failed to create item"`)であり、そのままユーザーに見せると実装が透けて見える上に
   日本語UIに英語が混じるため、detail 抽出案は見送った。

6. **8箇所(フォーム4つ・取得系4つ)に同じパターンが繰り返されることになるが、共通化(カスタムフック)を今回のproposalのスコープに含めるか、各ページ個別実装として先送りするか。**
   → 共通フックによる設計をスコープに含める。パターンが全ページで同形であり抽象化のリスクが低いこと、
   共通フックで loading/success/error を明示的に区別すれば「初期ロード失敗が永久ローディングになる」問題も
   副次的に解消できることから採用した。個別実装案は、後で結局同じ抽象化をやり直すことになるため見送った。

以上の回答を踏まえて `proposal.md` をまとめた。
