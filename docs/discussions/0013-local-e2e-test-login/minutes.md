## 「FakeVerifierの解決方法は一般的か」への回答

Web検索で調べた結果、業界でよく使われる2系統のパターンのどちらかに当てはまる、一般的な部類の
解決法だと分かった。

1. IdP境界そのものをモックし、それ以外の本物のコードパス（セッション生成・Origin検証など）は
   そのまま通す方式（[Xebia: Mock Your OpenID Connect Provider](https://xebia.com/blog/mock-your-openid-connect-provider/)）。
2. 認証フロー自体を丸ごとバイパスする開発専用のログインショートカット。Resource Owner Password
   Grant相当で、非本番限定という条件付きで許容される、と明記されている
   （[Autonoma: How to Test Auth0 Login](https://getautonoma.com/blog/how-to-test-auth0-login)）。

Playwright/Cypress公式推奨の「一度実ログインしてCookieを保存し再利用する」パターン
（storageState / `cy.session()`）はこのプロジェクトには当てはまらない。実Googleアカウントが
無く、`document.cookie` の直接注入もこの環境のブラウザ操作ツールのガードでブロックされるため、
そもそも一度も実ログインが成立しない。

## 質問と回答

### 1巡目

- **Verifierだけ差し替えるか、専用の直接ログインエンドポイントを新設するか**
  → Verifierだけ差し替え（`/api/auth/google` の本物のコードパス＝セッション生成・Origin検証を
  そのまま通す）を選択。
- **本番リークを防ぐ仕組みの強度（起動時env varチェック vs Go build tagでのコンパイル時除外）**
  → 起動時の環境変数チェック。CI/CD・デプロイ先がまだ未決定（0003が `proposed` のまま）なので、
  今のうちに決めておく余地があった。
- **想定利用者（Claude Codeのブラウザ自動確認専用か、人間の手動確認も含むか）**
  → Claude Codeのブラウザ自動確認専用。固定1ユーザーで足りる。

### 2巡目

FakeVerifierをどう組み込むかは決まったが、フロントエンドがGoogle Identity Servicesの本物の
スクリプトにしか繋がっていないため、「何をトリガーに `/api/auth/google` へPOSTするか」が
未解決だった点を指摘した。3案（HTMLフォーム送信のDev Loginボタン／fetch送信のDev Loginボタン／
`GET /api/auth/dev-login` への直接navigate）を提示。

→ ログインページにDev Loginボタン（HTMLフォーム送信）を選択。JS実行を伴わないため、ブラウザ
操作ツールのCookie/query stringガードに触れないはず、という理由。

## 検討したが採用しなかった案

- **専用の直接ログインエンドポイントで認証フローを丸ごとバイパス**: 実装は単純だが、
  セッション生成・Origin検証という本物のコードパスを一切通らなくなる。今回検証したいのは
  まさにこの「ボタンクリックでの一連の動作」なので不採用。
- **Go build tagによるコンパイル時除外**: 環境変数の設定ミスというクラスの事故は排除できるが、
  ビルド・CI設定が一段複雑になる。CI/CDがまだ未決定な現段階ではオーバーエンジニアリングと判断し、
  起動時env varチェックを採用。CI/CD構成が決まる際に強度を見直す余地は残る。
- **任意ユーザー・複数セッションに対応**: 想定利用者をClaude Codeのブラウザ自動確認に限定した
  ため、固定1ユーザーで十分と判断。人間の手動確認用途が今後出てきたら再検討。
- **fetch送信のDev Loginボタン**: 実装量はHTMLフォーム送信とほぼ同じだが、JSがセッションCookie
  取得に絡む形になり、ブラウザ操作ツールのガードに引っかかるリスクがHTMLフォーム送信より高いと
  判断し、より安全な方を選んだ。
- **`GET /api/auth/dev-login` への直接navigate**: フロントエンド変更が不要でブラウザ操作ツール
  との相性も一番良いが、実質的に「専用の直接ログインエンドポイントで認証フローを丸ごとバイパス」
  と同じ性質に近づくため、1巡目の決定と矛盾すると判断し不採用。

## proposal作成時に判明した技術的な制約

`POST /api/auth/google` はHumaで登録されたJSON専用のエンドポイントで、`credential` フィールドを
JSONボディとして読む。素のHTMLフォーム送信は `application/x-www-form-urlencoded` になるため、
このエンドポイントへ直接POSTすることはできない。

そのため、同一URLへの完全な同居はできず、セッション生成ロジック（Verify → Upsert →
期限切れセッション削除 → Session作成 → Set-Cookie）を関数として共有した上で、Dev Loginボタン専用
の新しいルート（JSON非依存、フォーム送信を受けられる）を新設する形にした。「Verifierだけ差し替え、
本物のコードパスを通す」という1巡目の決定の趣旨（セッション生成・Origin検証は完全に共有コード）は
保っているが、URLとリクエスト形式そのものは `/api/auth/google` と別になる。この点は決定を覆すもの
ではなく、決定を素直に実装に落とした結果の技術的な帰結として proposal に明記した。
