worklog [0004-item-groups-crud](../../worklogs/0004-item-groups-crud/README.md) の
「困難」節で、認証込みのブラウザ実地確認ができなかったことが記録されていた。実際の
Google アカウントと OAuth 認証情報が要るため実サインインができず、次善策として
`document.cookie` でセッション Cookie を直接注入しようとしたが、ハーネス側の
セキュリティガードにブロックされた、という話。そのときは「今後この種の機能を
実装するたびに同じ壁にぶつかるはずなので、ローカル専用のテスト用ログイン経路
(例: 開発環境限定で `FakeVerifier` を使う起動オプション)を用意するかどうかは、
別途検討の価値があるかもしれない」という一文で終わっていた。

worklog [0005-items-crud](../../worklogs/0005-items-crud/plan.md) で
アイテムCRUDを実装したときも、まったく同じ手順を踏んで、まったく同じ場所で
ブロックされた。`document.cookie = "__Host-session=...; path=/"` を実行しようと
したところ `[BLOCKED: Cookie/query string data]` という結果になった。代わりに
Firestore エミュレーターへ直接ユーザー・セッションドキュメントをシードした上で
`curl` から実サーバーに対して一連の CRUD 操作を行い、動作を確認した(これは0004と
まったく同じ回避策)。

一度目は「今後同じ壁にぶつかるかもしれない」という予測だったが、二度目で実際に
同じ壁にぶつかったことで、予測が的中した形になる。認証必須のCRUD機能を実装する
たびに、この環境では「ボタンを実際にクリックして動作を確認する」という最後の
一手が毎回欠けたまま実装を終えている。curl による API レベルの検証や、
モックした `fetch` によるフロントエンドのユニットテストでは代替できているが、
実ブラウザでのエンドツーエンドの動作確認だけは毎回できていない。

ローカル専用のテスト用ログイン経路(例: 開発環境限定で `FakeVerifier` を使う
起動オプションや、開発用の直接ログインエンドポイント)を用意する価値があるか、
検討したい。
