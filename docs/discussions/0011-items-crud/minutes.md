# 議事録

discovery.md の「アイテムグループのCRUDが出来たので、アイテムのCRUD操作も実装する。APIのみならず、
フロントエンドも実施。」という記述をもとに、実装範囲とURL・API設計を詰めた。

## 事前確認

discovery.md には frontmatter がなかった。date/tags/status/worklogs を追記し、ディレクトリ名を
`0011` から `0011-items-crud` へリネームした。

過去に同じ選択肢を検討して見送っている事実を最初に共有した。

- [0010: item groups](../0010-item-groups/proposal.md) で「グループだけでなくアイテムもフルCRUDで
  まとめて実装する案」は不採用だった。理由は「バックエンドが1つも実装されていない以上、範囲が広すぎる」。
  今回はその先送り分にあたる。
- 同じく0010で、アイテム詳細ページのURLについてフラットな `/items/:itemId` 案は不採用、ネストした
  `/groups/:groupId/items/:itemId` が有力候補として挙がったが決定はされておらず、今回に持ち越されていた。

あわせて関連する未決着事項も共有した。

- [0005: single resource get for groups and items](../0005-single-resource-get-for-groups-and-items/discovery.md)
  はグループ側が0010で解決済みだが、アイテム側(`GET /api/groups/{groupId}/items/{itemId}`)は
  `status: open` のまま残っていた。
- [0001](../0001-purpose-and-initial-tech-stack/proposal.md) で「アイテム一覧APIにはページネーションを
  設ける」こと自体は決定済みだが、方式・ページサイズは後続トピックへ保留されたままだった。
- worklog [0004-item-groups-crud](../../worklogs/0004-item-groups-crud/README.md) の「提案とのずれ」に、
  `ItemNewPage`/`ItemEditPage` が成功後に `navigate(`/groups/${groupId}/items`)` している(このURLは
  0010で廃止済み)という既知の不整合が記録されていた。

## 質問と回答

1. アイテム詳細ページを設けるかを確認した。グループと対称の「一覧→詳細→編集」構造にするため、設ける、
   という回答だった。
2. アイテム一覧APIのページネーションを今回決定・実装するかを確認した。今回は実装しない、0001の決定
   (「設けること」自体)は維持したまま方式は別議論に譲る、という回答だった。
3. アイテムの単体GETを今回のスコープに含めるかを確認した。含める、グループと同じ扱いにする、という
   回答だった。
4. アイテム詳細ページの中身と削除ボタンの配置を確認した。グループと同じ配置(詳細ページは表示+編集
   ボタンのみ、削除ボタンと確認ダイアログは編集ページ側)にする、という回答だった。
5. 作成・更新・削除成功後の遷移先を確認した。グループが一貫して `/groups`(一覧)に戻るのと同じ発想で、
   `/groups/:groupId`(グループ詳細、アイテムにとっての「一覧」に相当)に戻す、という回答だった。
6. `GroupDetailPage` のアイテム一覧の行リンク先(現状は編集ページへ直接)を、アイテム詳細ページ新設に
   合わせて変更するかを確認した。変更する、という回答だった。
7. アイテムAPIが対象groupIdの存在を事前検証するかを確認した。Firestoreのサブコレクションは親ドキュメント
   の存在を前提としないため、検証しないと削除済み/存在しないgroupId配下にアイテムを作成できてしまう
   点を指摘した。検証する(存在しないgroupIdは404)、という回答だった。
8. `DELETE` の冪等性(グループ削除と同じく常に204を返す方針)をアイテムでも踏襲するかを確認した。
   踏襲する、という回答だった。

## 検討したが採用しなかった案

- **アイテム詳細ページを設けず、一覧行から直接編集ページへ遷移させる案。** 不採用。グループとの対称性
  (一覧→詳細→編集)を優先した。
- **ページネーションの方式・ページサイズまで今回の議論で決定する案。** 不採用。スコープを広げすぎない
  ため、0001の決定(設けること自体)は維持しつつ方式は別トピックへ先送りした。
- **groupIdの存在を検証せず、パス構造を信頼してそのまま書き込む案。** 不採用。存在しない/削除済みの
  groupId配下に孤児データが作成され得るため、事前検証を採用した。
- **DELETEで存在しないitemIdの場合に404を返す案。** 不採用。グループ削除の冪等性方針(常に204)を
  アイテムにも一貫して適用した。ただしgroupId自体が存在しない場合は(groupId検証により)404になる。
- **アイテム詳細ページに削除ボタンも置く案。** 不採用。グループ詳細ページの配置(表示+編集ボタンのみ)
  をそのまま踏襲した。

## 結論

アイテムエンティティのCRUD(バックエンド新規実装+フロントエンドの再配線・詳細ページ新設)に範囲を
絞って合意した。ページネーションの方式、アイテムの別グループへの移動、API失敗時のエラー状態の具体的な
表示は、いずれも別トピックへ先送りする。詳細は proposal.md に記載する。
