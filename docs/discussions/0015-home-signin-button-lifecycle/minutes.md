# 議事録

対象: [discovery.md](discovery.md)。ホーム画面でログイン直後（リロードなし）に Google のサインイン
ボタンがアバターと共存して残る現象。[0009-home-with-auth](../0009-home-with-auth/proposal.md) と
同一の現象だが、0009 は proposal のみで未実装だったため「また出た」ではなく「ずっと直っていなかった
ものを再度踏んだ」もの。

## 事前に共有したこと（過去に見送られている選択肢）

- **専用 `/login` ページ**: [0004](../0004-home-and-login/proposal.md) が明示的に不採用。未認証
  ホームのボタンがその場でログインを起動する形にしていた。
- **認証済みは `/groups` へ直接リダイレクト**: [0004](../0004-home-and-login/minutes.md) が検討して
  不採用。アカウント表示のある認証済みホームを残していた。
- **0009 の A案（`key={state.status}`）**: 不採用ではなく「シンプルさ優先で採用」。ただし未実装。
  B案（`renderSignInButton` を呼ぶ `useEffect` にクリーンアップを足す）は次善案として記録されていた。
- **[decision 0002](../../decisions/0002-google-id-token-auth.md) / [0007](../0007-google-auth/discovery.md)（Accepted）**:
  フロントは常に Google 製 `renderButton()` の出力をレンダーする。プレーンボタン ＋ `prompt()` は不可。
- **[0016](../0016-visual-style-overhaul/proposal.md)（proposed）**: HomePage のマークアップを書き直す
  仕様。ただし「Google 製サインインボタン据え置き」で、まだコード反映前。

## 私が投げた質問と回答（＝欠けていた文脈）

1. **今回のセッションで B案は試したか、結果は。** → 試した。`useEffect` クリーンアップの
   `container.replaceChildren()` も `useLayoutEffect` 版も、注入ノードは消えるが **React が同じ
   `<div>` に描いたアバターと名前まで一緒に消えた**。クリーンアップ時点で `signInButtonRef.current`
   は React が既に null 化。→ 0009 の次善案は成立しないと確定。
2. **原因の切り分けに同意するか。** バグの原因は早期 return の3分岐構造そのものではなく、命令的
   `renderButton()` 注入 × React が位置でノードを使い回すこと。パッシブ effect のクリーンアップは
   React が新しいレンダーを使い回しノードにコミットし終えた後に走るため、そのノードに触ると
   アバターを掴む。→ 同意。
3. **スコープ。** (a) orphan バグを局所修正（`<GoogleSignInButton />` 抽出のみ） / (b) 加えて認証
   状態の画面切り替えをルート単位のパターンにし 0006 を取り込み 0004 の「`/login` なし」を再検討 /
   (c) 認証ルーティングの全面再設計。→ **(b)**。
4. **0016 との順序、0009 が未実装だった理由。** → 0015 を先にやる。0009 は「なんとなく気が乗らな
   かった」ので未着手。
5. **`/` と `/login` を分けるか。分けるならログイン成功後の着地は `/` か `/groups` か。** → 分ける。
   過去の決定を覆して `/groups` に着地してよい（認証済みホーム自体を廃止してよい、の意）。
6. **未認証で `/groups/xyz` に直接来たとき、ログイン後に元 URL へ戻すか、一律の着地か。** → 一律
   （`location` 退避なし）。
7. **`loading` 中にガードは何を出すか（全画面スケルトン / 各ページ自前 / 何も出さない）。ガードは
   `AppLayout` を1回包むか各ルート個別か。** → 各ページ自前。`AppLayout` のルート要素を1回包む。
8. **認証済みホームを廃止し `/` をリダイレクトのみにする、で合っているか。名前の表示場所が無くなるが
   どうするか（捨てる / `NavMenu` に出す / ホームを残す）。** → 合っている。**`NavMenu` のシート内に
   名前を出す**（本スコープに含む）。

## 検討したが採用しなかった案

同じものを proposal にも書くが、数か月後に再浮上したときの歯止めとしてここにも残す。

- **`key={state.status}`（0009 A案）**: 動くが対症療法。命令的注入 × 位置ベースの使い回し、という
  脆い構造が残り、認証 UI を触るたびにこの手を思い出す必要がある。ユーザーが明示的に脱したい形。
- **effect クリーンアップで Google 注入分だけ削除（0009 B案）**: Q1 のとおり今回検証して破綻。
  ノードが使い回される限り原理的に無理。
- **`/` を単一の分岐ページのまま、`/groups/*` だけガード**: 変更は小さく 0004 も触らずに 0006 は
  解けるが、`/` の orphan はコンポーネント抽出の規律頼みで構造的には塞がらない。scope (b) を選んだ
  理由に反する。
- **ポータル / detached ノード保持 / 常設して hidden**: ルート遷移で unmount する専用コンポーネント
  と同じ保証を、より多い仕掛けで得るだけ。「常設 hidden」は認証済み画面に生きた Google iframe を残す
  副作用もある。
- **深いリンクの復帰（`location` を退避して元 URL に戻す）**: 当面見送り。配線が増える。0006 の
  当初候補も「`/` へ」だった。一律 `/groups` 着地で足りる。
- **`loading` 中はガードが全画面スケルトン（Q7 の案）**: 各ページに既にローディング UI があり、
  ガードへ集約すると二重管理になる。各ページ自前を採用。トレードオフとして、未認証で `/groups/xyz`
  に来るとリダイレクト前に一瞬そのページのスケルトンが出て `/api/groups` が1回 401 になる。軽微
  として許容。
- **認証済みホームを残す（Q8 の案）**: ユーザーが却下。`/` はリダイレクトのみ、名前は `NavMenu` へ。
- **`<StrictMode>` を外す（[0017](../0017-duplicate-api-requests-on-load/minutes.md) で言及）**:
  この種のバグを炙り出す dev チェックなので外さない。代わりにボタンコンポーネント側を二重マウント
  安全にする。

## 結論

scope (b) で合意。ルート単位の認証ゲート（`<RequireAuth>` / `<RequireGuest>`）＋ `/` と `/login` の
分割 ＋ auth モジュールが公開する `<GoogleSignInButton />` コンポーネント。認証済みホームは廃止し
`/` はリダイレクトのみ、ユーザー名は `NavMenu` へ移す。0004 の2つの決定（`/login` なし／認証済み
ホームを残す）を覆し、0006 を吸収、0009 を supersede する。0016 より先に着手する。詳細は
[proposal.md](proposal.md)。
