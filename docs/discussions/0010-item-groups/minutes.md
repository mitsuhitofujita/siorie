# 議事録

discovery.md の「アイテムグループのCRUD操作を実装する。APIのみならず、フロントエンドも実施。」という記述と、
2つの操作フロー（作成→編集フロー、削除フロー）をもとに、実装範囲とURL設計を詰めた。

## 事前確認

discovery.md には frontmatter がなかった（他の全discussionにはある）。date/tags/status/worklogsを追記した。

tags が重なる過去のdiscussionのうち、以下2件は「検討して見送った」のではなく**未決定のまま今回の実装に直結する**ものだった。最初にその旨を共有した。

- [0005: single resource get for groups and items](../0005-single-resource-get-for-groups-and-items/discovery.md)（status: open）。
  編集ページの初期データ取得に単体GETが必要かが未決定のまま、`GroupEditPage.tsx` は「一覧を取得して `.find()` する」
  ワークアラウンドで実装されていた。
- [0006: unauthenticated route guard](../0006-unauthenticated-route-guard/discovery.md)（status: open）。
  未認証で `/groups` 以下に直接到達した場合の挙動が未決定のまま、バックエンド不在ゆえ素通しになっていた。

バックエンドの groups/items エンドポイントは1つも実装されていない（`server.go` にあるのは hello と auth のみ）ことも確認した。

## 質問と回答

1. discovery.md に frontmatter がない点を確認した。今回エージェント側で追加する、という回答だった。
2. 操作フローの「追加したアイテム詳細ページ」が、既存設計（0004: 一覧行から直接編集ページへ遷移、詳細ページなし）に
   ない新しい閲覧専用ページかを確認した。新設する、という回答だった。
3. 0005・0006を今回まとめて解決するかを確認した。0010の中でまとめて決める、という回答だった。
4. 「アイテムグループ」がグループ・アイテムどちらのエンティティを指すか（あるいは両方か）を確認した。
   グループエンティティのみで、アイテム側は既存のまま手を入れない、という回答だった。
5. グループの詳細ページの中身を確認した。既存の `/groups/:groupId/items`（アイテム一覧ページ）を拡張する案（URLは変えない）
   を提示したが、回答は「`/groups/:groupId` がグループの詳細・アイテムの一覧・編集ボタンを持つ」というもので、
   URL自体を `/items` サフィックスなしに変更する案だった。
6. アイテムの詳細ページ（`/groups/:groupId/items/:itemId` 相当）の要否を確認した。
   当初「ネストせず `/items/:itemId` という独立URLにする」という回答だったが、Firestoreのデータモデル
   （`groups/{groupId}/items/{itemId}`）との対応が崩れる点を指摘したところ、フラットURLは却下し
   Firestoreに自然な構造（ネスト）を優先する、との回答に変わった。
7. 質問4（スコープはグループのみ）と質問6（アイテム詳細ページのURL設計）が矛盾して見える点を指摘した。
   discovery.md の「追加したアイテム詳細ページ」は実はアイテムではなく**グループ自身の詳細ページ**を指す、
   という解釈で合意した。あわせて、アイテム側のURL設計（質問6の結論）はアイテムCRUD自体が今回スコープ外のため、
   将来アイテムCRUDに着手する議論へ持ち越すことに合意した。
8. グループ詳細ページに埋め込む「アイテムの一覧」の表示に必要な `GET /api/groups/{groupId}/items` を
   今回実装するかを確認した。今回は未実装、という回答だった（アイテム一覧欄は既存の未接続状態のまま）。
9. 0006の解決方式（各ページでのリダイレクト／401をエラー状態として扱う／AppLayoutでの一括ガード）を確認した。
   401をエラー状態として扱う（専用のガードは設けない）、という回答だった。
10. グループ名の文字数上限（0001で後続トピックへ保留されたまま未決定だった）を確認した。
    アイテムタイトルと同じ100文字でよい、という回答だった。
11. 一覧の行から直接編集ページへ遷移する既存のリンク（`GroupsListPage.tsx` の「編集」リンク）を廃止し、
    編集は必ず詳細ページ経由にするかを確認した。廃止する、という回答だった。

## 検討したが採用しなかった案

- **グループだけでなくアイテムもフルCRUDで今回まとめて実装する案。** 不採用。バックエンドが1つも実装されていない
  以上、範囲が広すぎると判断し、グループのみに絞った。アイテムのCRUDは将来の別議論に譲る。
- **グループ詳細ページを既存の `/groups/:groupId/items` のURLのまま、見出しと編集リンクを足す形で拡張する案。**
  不採用。`/groups/:groupId` という独立したURLをグループの詳細（名前＋アイテム一覧＋編集ボタン）とし、
  `/items` サフィックス付きのルートは廃止することにした。
- **アイテムの詳細ページを今回新設し、`/groups/:groupId/items/:itemId` へ遷移できるようにする案。** 不採用。
  アイテムCRUD自体が今回のスコープ外であるため、アイテム詳細ページの新設も将来のアイテムCRUD議論に持ち越す。
- **アイテム詳細のURLをグループから独立させ `/items/:itemId` というフラットな形にする案。** 不採用。
  Firestoreのデータモデルが `users/{uid}/groups/{groupId}/items/{itemId}` とグループ配下にネストされている点を優先し、
  採用するとしても `/groups/:groupId/items/:itemId` のネスト形式にする、という結論になった
  （ただし実装自体は将来議論に持ち越しのため、今回の提案には含めない）。
- **未認証アクセス時に各ページまたは `AppLayout` でリダイレクトガードする案。** 不採用。専用のガード機構は設けず、
  401を「API失敗時の一般的なエラー状態」として扱う方針を採用した。ただしエラー状態の具体的な表示自体は
  0004で先送りされたまま今回も未決定であり、この方針だけでは未認証アクセス時の見た目は当面変わらない。
- **一覧の行から直接編集ページへ遷移する既存の導線を維持する案。** 不採用。discovery.md の両フローが
  「一覧→詳細→編集」の順で、一覧から編集への直接遷移を経由しないため、詳細ページ経由に統一した。

## 結論

グループエンティティのCRUD（バックエンド新規実装＋フロントエンド再配線）に範囲を絞って合意した。
アイテムのCRUD、アイテム詳細ページのURL設計、エラー状態の具体的な表示は、いずれも別トピックへ先送りする。
詳細は proposal.md に記載する。
