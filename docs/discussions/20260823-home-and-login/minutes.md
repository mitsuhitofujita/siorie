# 議事録

discovery.md の記述をもとに、共通レイアウト・ホームページ・ナビメニュー・CRUDページ・URL設計・空状態を詰めた。

## 事前確認

tags が重なる過去の discussion はなかった。同じ選択肢を検討して見送った過去の議論もない。
ただし [purpose and initial tech stack](../20260823-purpose-and-initial-tech-stack/proposal.md) では
「画面構成と操作フロー」を後続トピックへ保留すると明記されており、本 discussion がその後続トピックにあたる。
認証フロー（Google Identity Services → ID Token 送信 → セッション発行）自体はそちらで確定済みであることを前提に進めた。

## 質問と回答

1. グループ・アイテムの作成ページと編集ページの関係を確認した。作成専用の別ページとする回答だった。
2. 認証済みホームページの内容を確認した。discovery.md の記述だとグループ一覧へはナビメニュー経由のみで、
   アプリの主目的（グループ管理）へのアクセスに一手間かかる設計になる点を指摘した。当初は「ナビ経由のままでよい」との回答だったが、
   後述の矛盾の指摘を受けて再検討し、最終的にホームページへ直接リンクとログアウトボタンを置く案に変わった。
3. フッターの「目立たないタイトル」の意味を確認した。アプリ名のみを控えめに表示する、という回答だった。
4. ログインページの有無を確認した。専用の `/login` ページは作らず、未認証ホームの「ログインボタン」がその場で
   Google ログインを起動する、という回答だった。
5. URL ルーティングをこの文書で決めるかを確認した。決める、という回答だった。
6. 空状態・ローディング状態をスコープに含めるかを確認した。含める、という回答だった。
7. エラー状態（API失敗時の表示）をスコープに含めるかを確認した。含めない、別トピックへ回す、という回答だった。
8. ホームページは共通レイアウトを使用しないためヘッダのアカウント画像タップによるナビメニューを開く起点がなく、
   「グループ一覧へはナビ経由」という回答と矛盾することを指摘した。

## 検討したが採用しなかった案

- **認証済みならホームページを作らず、直接グループ一覧ページへリダイレクトする案。** 質問2で提示したが不採用。
  最終的には、ホーム固有のアカウント情報表示は残しつつ、グループ一覧へのリンクとログアウトボタンを追加する折衷案を採用した。
- **グループ・アイテムの作成/編集/削除をモーダルやダイアログで完結させ、ページ遷移させない案。** 不採用。
  作成・編集はそれぞれ専用ページへの遷移とし、削除だけは編集ページ内の確認モーダルで扱う方式を採用した。
- **作成と編集を同一ページ（空の状態で開けば作成、既存データを読み込めば編集）として扱う案。** 不採用。
  作成専用の別ページとする方式を採用した。
- **認証済みホームのアカウント情報表示自体がナビメニューのタップ起点を兼ねる案。** 質問8への解決策として一度検討したが、
  最終的にはナビメニューに頼らず、ホームページへ「グループ一覧へのリンク」と「ログアウトボタン」を直接置く案を採用したため不要になった。
- **URL パス設計を実装時に委ね、この文書では画面構成・遷移のみを扱う案。** 不採用。今回の文書内で URL パスまで確定させることにした。
- **API 失敗時などのエラー状態の表示をこの文書に含める案。** 不採用。別トピックへ先送りすることにした。

## 結論

- 共通レイアウト、ホームページ（未認証／認証済み）、ナビメニュー、グループ・アイテムの CRUD ページ、
  URL 設計、空状態・ローディング状態について合意した。詳細は proposal.md に記載する。
- エラー状態の表示は別トピックへ先送りする。
